# Telegram-бот распределения остатков по FBS-складам Wildberries

## v17.4: доли кабинетов при дефиците и архив для диагностики

Если рассчитанного количества товара не хватает на полный страховой запас
4 шт. на каждый доступный склад, бот сначала делит это количество между
кабинетами пропорционально FBS-заказам за выбранный период. Затем доля каждого
кабинета распределяется по его складам: страховой минимум в пределах своей
доли, затем спрос. Например, 9 шт. при 1 и 2 заказах дают 3 и 6 шт.

Целые доли определяются методом наибольших остатков. При наличии хотя бы
одной единицы на каждый кабинет сохраняется минимум 1 шт. каждому доступному
кабинету, включая кабинет без заказов. При ещё меньшем наличии приоритет у
большего спроса. При отсутствии заказов доли выравниваются между кабинетами,
с учётом вместимости их страхового запаса. Названия кабинетов больше не
определяют их доли; при равных числовых приоритетах используется стабильный
внутренний ключ кабинета.

При дефиците доля кабинета может не покрыть даже по одной единице каждому
его складу: весь товар не разбрасывается по складам вопреки долям спроса.
Когда полного страхового запаса хватает, прежнее правило 4 шт. каждому
доступному складу и распределение остатка по заказам сохраняются.
Правило действует и для одиночных товаров, и для рассчитанных комплектов.
Логика распределения компонентов между рецептами не изменяется.

В общий ZIP теперь входят:

- Складские Excel в корне, как прежде.
- `report.json`: версия, параметры, итоги, связи с выходными ШК, заказы и
  выставленные количества по кабинетам и складам для каждого ШК, а также
  правило и входное количество каждого этапа распределения.
- `diagnostics/input.xlsx` или `.xls`: исходный файл этого расчёта.
- `diagnostics/kits_template.xlsx`, `exclusions.xlsx` (если загружены) и
  `stocks_template.xlsx`: копии файлов именно на момент расчёта.
- `diagnostics/calculation_snapshot.json`: исходные и нормализованные
  остатки, обычные и встроенные рецепты, каталог ШК/nmID/chrtID, альтернативные
  связи и кабинетные исключения, агрегаты заказов и минимальные поля заказов,
  которые позволяют проверить их подсчёт и повторить расчёт без WB.
- `diagnostics/manifest.json`: размеры и SHA-256 всех остальных файлов ZIP.

В `report.json` ищите ШК в `sku_diagnostics`; его `cabinets` показывают
заказы, доступность, выходной ШК и `allocated_total`. Раздел `allocations`
содержит итог и `distribution_details`: количество к распределению, требуемый
полный страховой запас, заказы каждого склада и квоты кабинетов при дефиците.
Связь альтернативных ШК видна через `alias_root` и `stock_barcode`.

Сохраняются фактические границы API-запроса заказов (`dateFrom`, `dateTo`),
версия отчёта и контрольные суммы модулей расчёта. Бот считает FBS-сборочные
задания за период по chrtID и доступным складам, а не число выкупов. Заказы
на недоступных складах/с некорректными идентификаторами можно сопоставить с
`orders_ignored` и снимком. Отфильтрованные кабинетными исключениями ШК
сохраняют исходную историю в снимке каталога и заказов.

Для разбора ошибки распределения достаточно прислать весь полученный ZIP.
`report.json` сохраняет прежние поля для совместимости; новые поля добавлены.
Архив создаётся до автоматической записи: журнал последующей операции WB
по-прежнему выдаётся отдельно. Токены, `.env`, Telegram ID пользователей и
полные ответы с адресами покупателей в диагностический отчёт не включаются.
Исходные файлы и каталоги содержат рабочие данные об ассортименте и остатках.

Обычные комплекты, два правила деления по 50, `%`, `!`, кабинетные исключения,
дата в имени архива, подтверждения, резервные копии, откат, обнуление и права
администраторов сохранены. При обновлении сохраните `.env` и папку `data`.

## v17.3: деление упаковок и общий расчёт с шаблоном комплектов

Встроены два специальных правила:

| Исходный ШК упаковки по 100 | Выходной ШК набора по 50 | Результат одного деления |
|---|---|---|
| 4610231972418 | 2046819245780 | Из 1 упаковки получаются 2 набора |
| 4610231972241 | 2046819266549 | Из 1 упаковки получаются 2 набора |

Добавлять эти два набора в шаблон не требуется. Наборы по 200, 300, 600 и
любые другие продолжают формироваться именно по загруженному шаблону:
повторение исходного ШК в компонентах задаёт расход исходных упаковок.
Например, для 200 нужны два исходных ШК по 100, для 300 — три, для 600 — шесть.
У каждой пары правил свой исходный запас; разные товары не смешиваются.

Наборы по 50 конкурируют за общий исходный запас с продажей упаковок по 100
и с комплектами из шаблона. Сначала учитывается страховой запас до 4 единиц
каждого варианта на склад при достаточном наличии, затем спрос за 14 дней.
Запас, выделенный одному варианту, больше не доступен остальным.
Счёт исходного товара остаётся в единицах его ШК, без перевода в отдельные
штуки содержимого и без автоматического умножения или деления входного количества на 100.

Новое деление выполняется только целыми исходными упаковками, поэтому общее
количество вновь созданных наборов по 50 всегда чётное. По складам полученные
наборы можно распределять поштучно. Нечётный спрос при достаточном запасе
округляется вверх до пары; количество исходных упаковок остаётся целым.
Если готовые наборы по 50 уже имеют положительный остаток во входном файле,
они распределяются самостоятельно без дополнительного деления, как в v17.2.
Положительный остаток упаковки по 100 разрешено использовать как компонент.

`%`, `!`, кабинетные исключения и альтернативные ШК сохраняют свои правила.
`%` у набора по 50 запрещает деление и даёт нулевой выход, а исходный запас
остаётся доступен остальным комплектам. `!` у исходного ШК запрещает его
расходование на комплекты. При `%` или `!` у готового набора его защита
не отменяется встроенным правилом.

Если тот же выходной ШК по 50 уже есть в шаблоне, для него применяется
встроенное правило деления. Все остальные рецепты берутся из шаблона без
изменений. Дублирующие альтернативные строки набора или совпадение chrtID
исходной упаковки и выходного набора останавливают расчёт с объяснением.

В `report.json` у комплектов добавлены поля `output_per_batch` (выход за
один цикл), `batches` (число циклов) и `component_units_consumed` (реально
израсходованные компоненты). Поле `components` описывает компоненты одного
цикла: у обычного комплекта выход 1, у встроенного деления — 2.
`component_consumed_by_kits` остаётся общим фактическим расходом исходных ШК.

Дата в имени ZIP, отправка только общего архива, сравнение перед записью,
подтверждения, резервные копии, проверка записи, откат, аварийное обнуление
и права администраторов действуют как в v17.2.1. При обновлении сохраните
`.env` и всю папку `data`, включая рабочий шаблон комплектов.

## v17.2.1: дата в имени архива

Итоговый архив называется `Распределение_FBS_ДД.ММ.ГГГГ.zip`, например
`Распределение_FBS_13.10.2026.zip`. Дата определяется при создании архива
по московскому времени (UTC+3), независимо от часового пояса хостинга.

## v17.2: готовые комплекты, знак % и общий архив

Входной файл `.xlsx` или `.xls`: колонка «Код» / «Баркод» / «ШК» и
«Доступно» / «Наличие» / «Количество». Новые правила действуют для обоих
кабинетов и всех согласованных альтернативных ШК одной вариации.

| Значение в наличии комплекта | Поведение |
|---|---|
| Положительное число | Распределить имеющиеся готовые комплекты как самостоятельный товар; не собирать дополнительно из компонентов |
| `%` (текстовый знак вместо количества) | Не собирать комплект; выставить ему 0 в складских Excel и при подтверждённой автоматической загрузке |
| `0` или ШК отсутствует во входном файле | Разрешить сборку из компонентов по прежним правилам |
| `!` | Не распределять и не изменять остатки этой вариации, как раньше |

Для готовых комплектов сохраняются распределение по заказам за 14 дней,
страховой запас до 4 шт. на каждый доступный склад и прежние правила резерва
и округления. Компоненты не списываются на готовые или запрещённые через `%`
комплекты; они остаются для одиночных товаров и других разрешённых комплектов.
В сообщении «Собрано комплектов из компонентов» учитывается только фактическая
сборка, готовые комплекты входят в физический остаток входного файла.

Если у альтернативных ШК есть и `%`, и положительное количество, `%` имеет
приоритет для всей вариации независимо от порядка строк. `!` имеет приоритет
над `%`. Кабинетные исключения сохраняются: исключённые позиции не изменяются
даже при `%`. Противоречивые связи ШК/chrtID, не позволяющие безопасно применить
`%`, останавливают расчёт с объяснением. Знак `%` предназначен для комплектов:
если соответствующая вариация не найдена в шаблоне комплектов, файл отклоняется.
Управляющие знаки относятся к текущему расчёту и не изменяют шаблон комплектов.

Кнопки «Получить общий архив» и «Скачать архив и загрузить» отправляют только
один ZIP с файлами всех складов и `report.json`. Отдельные складские Excel
в Telegram больше не отправляются. Файл предварительного сравнения и журнал
операции WB по-прежнему отправляются отдельно при автоматической загрузке.

`report.json` содержит `ready_kit_barcodes`, `zero_kit_barcodes` и
`zero_kit_variant_groups` для проверки применения новых правил.
Подтверждения, резервные копии, откат, аварийное обнуление и права
TELEGRAM_ADMIN_IDS сохранены из v17.1. При обновлении сохраните `.env` и `data`.

Разделы ниже описывают историю возможностей; при расхождениях используйте
правила последней версии и последующих обновлений страхового запаса.

## Что делает

1. Принимает `.xlsx` с колонками **Баркод** и **Количество**.
2. Работает одновременно с двумя кабинетами WB.
3. Получает все FBS-склады продавца через `GET /api/v3/warehouses`.
4. Получает сборочные задания FBS за последние 14 дней через `GET /api/v3/orders`.
5. Получает карточки и все связанные с размером ШК (`skus`) через `POST /content/v2/get/cards/list`.
6. Для одинакового ШК в двух кабинетах считает единый физический остаток и распределяет его между всеми складами обоих кабинетов пропорционально заказам.
7. Создаёт отдельный Excel: `Кабинет — Название склада.xlsx`.
8. Хранит входной файл, выходные файлы и `report.json` 4 дня, затем удаляет.
9. Доступ ограничен белым списком Telegram ID.

## Правила распределения

- На каждый подходящий FBS-склад — минимум 1 шт., если физического остатка хватает.
- Если товара меньше количества складов, по 1 шт. получают склады с максимальным числом заказов за 14 дней.
- Если история заказов есть, остаток сверх минимальных единиц распределяется пропорционально заказам.
- Если количество **<= 20**, распределяется весь остаток; остаточные единицы после округления получают склады с наибольшей дробной долей/спросом.
- Если количество **> 20**, распределение округляется вниз, дробный хвост остаётся в резерве.
- Если истории заказов нет, сначала выдаётся по 1 шт. на склад, затем по возможности каждый склад доводится до 2 шт.; лишнее остаётся в резерве.
- Текущие остатки FBS не учитываются.
- Активные сборочные задания отдельно не вычитаются: они уже являются заказами.
- Если ШК не найден ни в одном кабинете, весь его остаток остаётся в резерве, а бот выводит конкретный ШК предупреждением.

## Требования к токенам WB

Оба токена должны иметь права как минимум на категории:

- **Маркетплейс** — склады продавца и FBS-заказы;
- **Контент** — карточки товаров, размеры и массивы `skus`.

Проще всего использовать токены с нужными разрешениями в одном ключе на каждый кабинет.

## Переменные окружения

См. `.env.example`.

Названия кабинетов задаются через `WB_CABINET_1_NAME` и `WB_CABINET_2_NAME`; они используются в названиях выходных файлов.

## Важное замечание

Бот считает **сборочные задания FBS**, а не выкупы: это соответствует правилу «учитывать заказы». Метод `/api/v3/orders` возвращает `warehouseId`, `chrtId`, `skus` и дату создания заказа, поэтому распределение строится именно по виртуальному складу продавца.

## Обнуление старых FBS-остатков

Каждый сформированный файл склада содержит полный список доступных баркодов соответствующего кабинета WB. Если товар не распределён на конкретный FBS-склад, в файле для этого ШК записывается `0`. Это нужно, чтобы при загрузке нового файла Wildberries обнулял остатки, выставленные ранее, но отсутствующие в сегодняшнем распределении.

## Главное меню и комплекты

В `/start` доступны две кнопки:

- **📦 Загрузить файл для распределения остатков** — обычный файл `Баркод | Количество`.
- **🧩 Загрузить шаблон комплектов** — сохраняет новый действующий шаблон до следующего обновления.

Шаблон комплектов: `Название | баркод комплекта | баркод1 | баркод2 | ...`.
Колонка `Название` информационная и в расчётах не участвует. Повтор одного и того же
баркода в составе означает кратность: например `A | A | A` = три единицы товара A
на один комплект.

Логика при распределении:

1. Сначала резервируется минимум по 1 шт. одиночного товара на каждый FBS-склад,
   где этот товар доступен. Это приоритет одиночных SKU.
2. Из оставшегося физического остатка формируются комплекты. Каждый комплект имеет
   собственную историю заказов за 14 дней и распределяется по своим продажам.
3. Если одного компонента не хватает на несколько комплектов, выше приоритет у
   комплекта с большим числом заказов за 14 дней; при равенстве — порядок строк шаблона.
4. После формирования комплектов остаток компонентов снова распределяется как
   одиночный товар по обычному алгоритму.
5. Если комплект не найден ни в одном кабинете WB, компоненты под него не резервируются,
   а бот выводит отдельное предупреждение.
6. Шаблон комплектов хранится в `data/kits_template.xlsx` и не удаляется очисткой
   4-дневной истории. В проект также включён `templates/kits_template.xlsx` как
   первоначальный шаблон.

## v11 — несколько ШК у одной товарной вариации

Бот группирует все SKU одного `chrtID` как один товар. В каждом файле склада для
одного `chrtID` выводится только один выбранный баркод. Альтернативные SKU этого
же `chrtID` не добавляются отдельными строками с нулём, поэтому загрузка остатков
не может обнулить товар вторым ШК. Если во входном файле указано несколько SKU
одного `chrtID`, их физический остаток суммируется и распределяется один раз.

## v12 — приоритет комплектов между базовым и страховым остатком

Порядок распределения физического товара:
1. минимум 1 шт. одиночного товара на каждый доступный FBS-склад;
2. комплекты по спросу за 14 дней (минимум присутствия — 1 комплект на склад, если хватает компонентов);
3. оставшимся одиночным товаром страховой запас поднимается слоями до `SAFETY_STOCK_PER_WAREHOUSE` (по умолчанию 4);
4. остаток сверх страхового запаса распределяется по продажам.

Это исправляет ситуацию, когда страховой запас 4 шт. полностью блокировал сборку комплектов при небольшом остатке.

## 💰 Сравнить цены (добавлено в v13)

В главном меню появилась **💰 Сравнить цены** → **1 неделя** или **2 недели**.
Отдельный, только читающий модуль `app/price_compare.py`; алгоритм распределения
остатков, комплектов, нулевых строк и ручных исключений **не изменён**.

Отчёт `.xlsx` содержит только товары, обнаруженные **в обоих кабинетах** по
пересечению баркодов; несколько ШК одной товарной вариации каждого кабинета
объединяются. При неоднозначном соответствии вариантов строка исключается,
количество таких случаев указано в результате. Поля: общий ШК, артикул продавца,
текущая цена продавца со скидкой (`discountedPrice`, без WB/клубных скидок),
заказы кабинетов 1/2 (в штуках), процентная разница заказов относительно
кабинета 1, процентная разница цен, все ШК соответствующей вариации в каждом
кабинете. При нулевых заказах кабинета 1 разница в процентах остаётся пустой.

Заказы берутся за 7/14 **полных** календарных дней (по московскому времени,
сегодня не включён) через официальный отчёт статистики WB: **FBO + FBS**, без
отмен. Этот отчёт может обновляться с задержкой и не гарантирует учёт заказов
с неподтверждённой оплатой. В файле фиксируется **текущая** цена на момент
запуска, не исторические цены на даты каждого заказа. Поэтому отчёт не
доказывает, что различия спроса обусловлены только различием цен.

Ключам `WB_TOKEN_1` и `WB_TOKEN_2` необходимы права «Контент», «Цены и
скидки», «Статистика». Если права разделены между токенами, задайте необязательные
`WB_PRICES_TOKEN_1/2` и `WB_STATS_TOKEN_1/2` в переменных окружения.
По API WB выгрузка заказов может содержать около 80 000 строк за один запрос;
при достижении ограничения бот завершит запрос с ошибкой, а не отправит
неполный отчёт.


## v14 — совместное распределение одиночных товаров и комплектов

Для каждого товара и комплекта сначала резервируется страховой минимум до 4 единиц на каждый доступный FBS-склад, насколько позволяет общий физический остаток. Комплект резервируется только при наличии полного состава. После страхового минимума общий запас компонентов распределяется между продажей поштучно и комплектами по количеству заказов за последние 14 дней с учётом расхода компонентов на комплект. Заказы комплектов сверх страхового минимума ограничивают формирование комплектов. При нехватке компонентов полный страховой минимум для всех позиций не гарантирован; отрицательные остатки и виртуальные комплекты запрещены. Функция сравнения цен v13 не изменена.

### v15 — остатки в отчёте «Сравнить цены»

После заказов каждого кабинета выводятся остатки FBO, FBS и их сумма.
FBO: актуальный отчёт Аналитики WB по складам WB (поле `quantity`, без товаров в пути); FBS: сумма опубликованных остатков по всем FBS-складам кабинета. Эти цифры — срез на момент выгрузки, не остатки на дату заказов. Общий физический запас FBS двух кабинетов может пересекаться; не складывайте остатки двух кабинетов как уникальный физический запас.
Для FBO требуется категория токена «Аналитика»: при необходимости укажите `WB_ANALYTICS_TOKEN_1` и `WB_ANALYTICS_TOKEN_2` в `.env`. Для FBS используется основной токен с категорией «Маркетплейс». При ошибке получения остатков отчёт не формируется, чтобы не выдавать нули вместо неизвестных значений.

## v16 — исключения ШК по кабинетам

В главном меню добавлена кнопка **🚫 Исключения ШК**. Внутри доступны:

- **📥 Скачать шаблон** — бот отправляет текущий сохранённый файл исключений;
- **📤 Загрузить исключения** — принимает `.xlsx`/`.xls` и сохраняет его в `data/exclusions.xlsx` до следующего обновления.

Формат: `ШК | ID кабинета 1 | ID кабинета 2`. Если в колонке конкретного кабинета
указан ID продавца, этот ШК запрещён только для этого кабинета. Пустая ячейка означает,
что ШК разрешён. Бот сверяет введённый ID с `sid` продавца из соответствующего WB-токена. Если `sid`
не удаётся прочитать из токена, можно явно задать `WB_CABINET_1_ID/2` в `.env`. При
несовпадении ID файл не сохраняется и бот показывает ошибку.

Исключение применяется до выбора выходного ШК товарной вариации. Поэтому запрещённый
ШК не может снова появиться через объединение альтернативных ШК одного `chrtID`, не
получает страховой остаток и не добавляется в файл даже нулевой строкой. Если у того же
`chrtID` в кабинете есть другой разрешённый ШК, общий физический остаток может быть
распределён через разрешённый ШК. Если запрещены все ШК вариации в кабинете, вариация
не участвует в распределении на этом кабинете.

Старое правило `!` во входном файле не менялось: оно по-прежнему исключает всю
товарную вариацию глобально из автоматического распределения.

### v16.1 — исправление скачивания шаблона исключений

Кнопка «📥 Скачать шаблон» больше не зависит от наличия файла в `templates/`.
Если `data/exclusions.xlsx` уже существует, бот отправляет текущий файл исключений.
Если файла ещё нет, бот автоматически создаёт корректный XLSX с колонками
«ШК», «ID кабинета 1», «ID кабинета 2» и отправляет его пользователю.


### v16.2 — защита от конфликтующих ШК между кабинетами

Если два ШК числятся **разными `chrtID` в одном кабинете**, они не
объединяются в общий физический остаток только потому, что другой кабинет
поместил их в одну вариацию. Это предотвращает ситуацию, когда остатки
`4600987012223` (37 шт.) и `4600987012193` (60 шт.) превращались в один
общий пул 97 шт. При этом для каждого `chrtID` на конкретном кабинете
по-прежнему выгружается один разрешённый ШК; кабинетные исключения работают
как раньше. Конфликты каталогов записываются в `report.json` в поле
`diagnostic.conflicting_alias_variants`.

Если положительный остаток есть в выгруженном Excel, но не появляется в
личном кабинете WB, проверьте результат загрузки файла/ошибки импорта: это
отдельный процесс, который данный патч не контролирует.

## v17: автоматическая загрузка FBS, сравнение, резервные копии, откат и аварийное обнуление

**Безопасность:** автоматические операции с WB выполняются **только** по отдельному
подтверждению администратора. По умолчанию запись в WB отключена для всех:
добавьте `TELEGRAM_ADMIN_IDS=ваш_Telegram_ID` в `.env` (ID также должен быть
в `TELEGRAM_ALLOWED_IDS`). Основные `WB_TOKEN_1` и `WB_TOKEN_2` должны иметь
категорию **Маркетплейс** с правом записи и **Контент** для каталога.

**Сценарий распределения:** загрузите Excel как раньше → бот рассчитает
распределение → предложит «Получить Excel-файлы», «Загрузить на WB» или
«Скачать и загрузить». При загрузке выберите оба кабинета или один,
бот прочитает текущие остатки по `chrtID` через `POST /api/v3/stocks/{warehouseId}`
и пришлёт сравнение Excel «Было → Станет → Разница». Только после
подтверждения он выполнит `PUT /api/v3/stocks/{warehouseId}` для **изменённых**
позиций. Перед отправкой сверит текущие остатки с предпросмотром; если они
изменились, операция будет отменена без отправки. После каждого запроса
проверит значения повторным чтением.

**Откат:** кнопка «↩️ Откатить загрузку» восстанавливает сохранённые остатки
последней операции бота. Восстанавливаются только позиции, успешно
подтверждённые после обновления, и только если текущие значения WB по ним
совпадают с результатом того обновления. Позиции, изменившиеся из-за заказов,
ручных действий или других сервисов, **пропускаются**. Выбирается кабинет;
откат одного кабинета не блокирует откат второго. После предпросмотра
необходимо подтверждение.

**Аварийное обнуление:** кнопка «🛑 Аварийное обнуление FBS» → выбор кабинетов →
сравнение → кнопка продолжения → **ввод `ОБНУЛИТЬ`** → финальная кнопка.
Бот запрашивает все известные `chrtID` из **активного каталога** и обнуляет
только ненулевые FBS-остатки на выбранных складах. Это включает товары,
которых нет в последнем Excel. Кабинетные исключения защищены при загрузке,
обнулении и откате. Если запрещённый и разрешённый ШК имеют общий chrtID,
автоматическая запись пропускает весь chrtID: WB хранит остаток по размеру,
раздельно изменить остатки его ШК нельзя. Расчёт и Excel сохраняют прежние правила.
Количество пропущенных позиций показано в предпросмотре. Изменение файла
исключений после сравнения требует нового предпросмотра.
Кнопка «Выбрать склады» позволяет отметить несколько складов обоих кабинетов.
**Ограничение API:** метод чтения FBS требует явного списка `chrtID`; поэтому
товары, которых нет в активном каталоге WB, могут не попасть в обнуление.
Нельзя гарантировать абсолютное обнуление *всех* товаров, если WB не
возвращает их в каталоге. Остатки FBO не затрагиваются.

**Резервные копии:** перед первым запросом на изменение создаётся JSON-журнал
в `data/stock_operations/records/`, включая предыдущие значения WB и список
предстоящих изменений. После каждого запроса журнал обновляется с указанием
подтверждённых позиций и ошибок. В меню показываются 10 последних операций;
резервные копии на диске автоматически не удаляются. Предпросмотр действует 15 минут и сбрасывается после
перезапуска бота. Не удаляйте папку `data/stock_operations/` при обновлении
или перезапуске. В меню «📂 История загрузок» доступно скачивание резервной
копий десяти последних операций.

**Важно:**
- Это **не** транзакция WB: отдельные склады могут обновиться, а другие нет.
  Проверяйте отчёт и историю. При сбое хостинга во время PUT журнал может
  иметь статус `started`: проверьте фактические остатки и резервную копию
  вручную, прежде чем повторять операцию.
- При работающем боте в **одном процессе** нельзя одновременно запустить
  две операции; **не запускайте две копии бота** с одинаковыми токенами и
  общей базой. Внешние сервисы, меняющие FBS, также могут создавать конфликты.
- Отправка количества `0` не удаляет карточку товара и не отменяет уже
  поступившие заказы. Данные WB могут обновляться с задержкой.
- Для отката после продаж безопаснее пропустить изменившиеся позиции, чем
  восстановить количество, которое уже было продано.
- Автоматическую запись **невозможно проверить на реальном WB без ваших
  токенов и тестовой операции**. Сначала проверьте загрузку на одном кабинете.

Официальная документация: https://dev.wildberries.ru/openapi/work-with-products

### Проверка v17.1

Права записи согласованы: только пересечение TELEGRAM_ALLOWED_IDS и
TELEGRAM_ADMIN_IDS. Несколько администраторов перечисляются через запятую.
Откат накапливает успешно восстановленные позиции, в том числе при частичной
ошибке; повторный откат не пытается восстановить их ещё раз.
PUT не повторяется автоматически при тайм-ауте или серверной ошибке:
бот читает результат, поскольку повторная запись могла бы затереть новый заказ.
Проверка перед записью не является атомарной блокировкой WB: внешний заказ
между чтением и записью всё ещё возможен.

Тесты: `python -m pip install -r requirements.txt pytest`, затем `python -m pytest -q`.
Все сетевые операции в тестах заменяются имитацией WB; токены не нужны.
